# 网约车需求建模：调研与架构选择依据

调研日期：2026-11-11。本文记录实施前的技术比较与建议；最终接口、运行方式与已验证范围以交接文档为准。以下“建议”属于结合课题规模的工程判断，不代表引用材料对该项目的实验结论。

## 1. 先明确预测对象

建议将主目标定义为：**给定区域、给定时间桶内新发起的叫车请求数**，单位“单/区域/时间桶”。乘客人数、完成订单数、可用车辆数和未满足请求分别保存，避免把不同口径混成“需求”。

公开真实数据常有观测边界。纽约 TLC 官方资料记录接送时间、区域、行程等；乘客数是部分出租车数据中的司机填报字段；FHV 字段与出租车字段不同。TLC 同时提示数据的准确性与完整性存在限制。因此，只有已完成/已实现行程的数据，只能支持“已观测出行量”预测；不能直接声称得到所有潜在请求，或把缺少记录解释成没有需求。[TLC 数据说明](https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page)

虚拟世界可以生成完整的请求流，再由供给与调度决定服务结果，因而能够保留“请求→匹配→完成/未满足”的因果方向。训练数据必须标注 `source=synthetic`；真实数据标注 `source=imported`，保留原始字段映射、时间口径和质量报告。仿真上的较好指标不能作为真实城市上的有效性证明。

## 2. 架构候选与推荐

| 方案 | 优点 | 代价/适用条件 | 本课题选择 |
| --- | --- | --- | --- |
| 模块化单体 API + CLI/独立 worker + SQLite | 安装与演示简单；业务层、仿真和机器学习仍可清楚分离 | 单机容量与单写者限制 | 推荐首期交付 |
| FastAPI + PostgreSQL/PostGIS + Redis/Celery | 并发、空间查询、任务扩容更成熟 | 运维组件多，需要数据库迁移与消息队列治理 | 有真实用户和多机需求后演进 |
| 多微服务 + Kafka/流式特征平台 | 可独立扩缩、支持高吞吐在线特征 | 故障面、数据一致性与部署复杂度明显增加 | 不宜作为课程系统起点 |

SQLite 的 WAL 模式允许读写并行，但同时仍只有一个写者，并且需要同机共享内存，不能把 WAL 数据库直接放在网络文件系统上。建议短事务、写入批次控制、明确的锁超时与单个训练任务并发上限。[SQLite WAL 官方说明](https://www.sqlite.org/wal.html)

长耗时训练不应占住 HTTP 请求。FastAPI 官方对重计算提出采用进程/服务器外的任务工具（例如 Celery）的建议。本课题可先采用独立 CLI/worker 与持久化任务记录，API 负责提交和查询状态；如果采用本进程执行器，应在交接中明确重启恢复、并发和单进程的限制，不能当作分布式可靠队列。[FastAPI Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/)

建议业务层划分为：`world`（区域、地图与事件）→`simulation`（请求与供需演化）→`datasets`（统一导入和质量控制）→`features`（时间窗口与外生变量）→`training`（实验与评估）→`inference`（预测与模型加载）→`api`（协议与校验）。依赖由外向内，训练层不导入 FastAPI；API 不直接拼特征。使用同一套特征代码保证训练与推理一致。

## 3. 虚拟世界怎样做到可复现、可替换

首期建议区域网格/显式区域图，而不是把系统与某个在线地图供应商绑定。世界至少包含：区域几何、区域类型（住宅/办公/商业/交通枢纽等）、邻接道路、道路距离或通行时间、车辆供给、日内/周内周期、天气、节假日、活动、道路扰动和随机波动。地图同时输出 GeoJSON 与区域 ID，前端可使用任意地图渲染器。

GeoJSON 坐标按经度、纬度排列，使用 WGS84 十进制度。虚拟坐标应保留 `synthetic` 元数据，不冒充真实底图；导入真实区域时校验坐标顺序、几何与区域 ID。[RFC 7946](https://datatracker.ietf.org/doc/html/rfc7946)

推荐生成过程：区域静态强度×时间曲线×天气/假日/活动倍率产生请求强度，再从计数分布抽样；目的地按可解释的 OD 权重抽样；通过道路图估计行程时间，车辆完成行程后更新可用位置。未满足请求不能从训练标签中删除。车队守恒、道路可达、种子重放、负载边界属于需要测试的模型约束。

微观交通仿真不是需求预测的必要前提。SUMO 已支持出租车/需求响应交通以及多种调度方式，可作为以后分析路口拥堵、车辆细粒度轨迹、拼车和真实路网时的扩展；首期自带轻量区域仿真能降低环境依赖。[SUMO 官方 Taxi 文档](https://github.com/eclipse-sumo/sumo/blob/main/docs/web/docs/Simulation/Taxi.md)

所有随机数使用显式种子与局部随机发生器。仿真配置、世界版本、时间范围、时区、生成器版本和种子一起写入数据集清单。天气、节假日和活动应由可替换适配器提供；真实节假日包含调休等地方规则，不可仅以周六/周日替代。

## 4. 模型候选：先建立可信基线，再增加结构

| 候选 | 表达能力 | 交付与数据要求 | 建议 |
| --- | --- | --- | --- |
| 最近值/上日同期/上周同期/历史时段均值 | 易解释，能识别周期是否已足够 | 很低 | 必备基线 |
| MLP + 滞后量 + 时间/区域/外因特征 | 适合小规模、多区域共享参数 | 实现、序列化和调试简单 | 有效首期深度模型候选 |
| GRU/LSTM + 静态区域特征 + 未来已知外因 | 学习时间动态；邻域需求可作为输入 | 训练与推理窗口一致 | 推荐序列模型候选 |
| ConvLSTM / ST-ResNet | 利用规则网格中的空间结构 | 固定网格；换区域需要重新编码 | 固定大网格后比较 |
| GCN+LSTM / DCRNN | 适合非规则区域和道路图 | 需可靠邻接图、更多数据和调参 | 后续研究扩展 |

TensorFlow 官方时间序列教程涵盖单步、多步、一次性输出与自回归预测。这里建议优先直接输出所需预测范围，或者按“一步模型+明确递推”实现；两者均需在评估和 API 中公开步长与预测起点，不把一步结果冒充多步精度。[TensorFlow 时间序列教程](https://www.tensorflow.org/tutorials/structured_data/time_series)

Keras 官方交通预测示例说明如何结合图卷积与 LSTM 利用相邻路段信息，适合作为升级路径。该示例预测的是道路速度，不能将其指标直接移用于订单请求数。[Keras 图时序预测示例](https://keras.io/examples/timeseries/timeseries_traffic_forecasting/)

ST-ResNet 原论文以空间划分中的流入/流出为目标，建模时间接近性、周期和趋势；DCRNN 在有向图上以扩散建模空间关系。它们为网络设计提供依据，但不意味着在本项目的小规模合成数据上一定胜过轻量模型。[ST-ResNet 原论文](https://arxiv.org/abs/1610.00081)、[DCRNN 原论文](https://arxiv.org/abs/1707.01926)

计数输出应非负，例如使用 softplus 或在预测层作非负约束。Poisson 损失与计数均值建模相适应，但真实订单可能过度离散；也可比较 `log1p` 目标的 MSE/Huber，并在原始单数尺度报告指标。不能仅以训练损失判定架构最好。[Keras 损失 API](https://keras.io/api/losses/)

## 5. 防止时间泄漏的完整协议

建议以时间顺序划分训练、验证、测试；每个时间桶的所有区域进入同一分区。先确定时间边界，再构造窗口；若允许验证/测试窗口使用边界以前已经发生的历史输入，应确保目标完全在各自分区内，且预测起点之前的数据才可读取。不要按区域行随机划分，也不要让同一个目标出现在训练与测试。

标准化统计量仅由训练分区估计。TensorFlow 官方教程明确采用时间顺序分割并只使用训练集的均值与标准差，目的就是防止验证/测试信息进入模型。[TensorFlow 分割与归一化示例](https://www.tensorflow.org/tutorials/structured_data/time_series)

时间、工作日、事先公布的节假日和活动属于未来已知变量；预测期真实天气、真实完成订单、真实到达车辆和真实乘客人数并非天然已知。真实应用中应输入在预测起点可取得的天气预报及其发布时间，或者只使用历史天气。合成世界可以显式允许“场景已知天气”，但必须在指标中标注这是条件预测，避免用未来实际天气制造过于理想的结果。

调参只使用验证集，早停与学习率调整监控验证误差。Keras `EarlyStopping` 可恢复最佳轮次权重；该行为需要显式启用 `restore_best_weights`，默认并不会恢复。[Keras EarlyStopping](https://keras.io/api/callbacks/early_stopping/)

最终报告建议包括：MAE（单）、RMSE（单）、WAPE、sMAPE、按区域/时段/天气/活动切片误差，以及与基线的差值。零需求时 MAPE 容易失真，不能把它作为唯一主指标；WAPE 在整个评价样本真实总量为零时也必须定义为空或使用明确约定。未来可增加滚动起点评估来检验不同时间段稳定性。[scikit-learn 时间序列交叉验证](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html)

如果提供区间预测，应说明是验证残差估计、分位数回归还是其他校准方式，报告测试区间覆盖率和区间宽度；不能把一个任意的固定百分比误差带称作“95%置信区间”。仿真中的反事实调度收益也只能标注为仿真结果。

## 6. 模型与数据生命周期

每个实验保存：数据集 ID/摘要、世界摘要、特征列表与顺序、时区与时间桶、训练/验证/测试边界、超参数、随机种子、依赖版本、训练历史、验证/测试指标、基线指标、模型文件和预处理状态。推理时校验特征模式、世界/区域集合和历史窗口，不能静默接受不兼容数据。

Keras 3 的原生持久化格式为 `.keras`；`model.save()` 保存 `.keras` 与 `model.export()` 输出 SavedModel 的用途不同。建议只采用内置层与可序列化配置，避免闭包/Lambda 作为关键计算造成交接后无法重新加载。[Keras 序列化指南](https://keras.io/guides/serialization_and_saving/)、[Keras 3 迁移指南](https://keras.io/guides/migrating_to_keras_3/)

训练与部署不要通过覆盖同一个文件完成切换。将新模型写入独立版本目录，验证可重新加载后再原子切换活动指针；旧版本保留以便回滚。API 响应附模型版本、预测起点、数据来源与条件假设。模型落后或不可用时，返回明确错误或有标签的基线回退结果，不伪装成神经网络预测。

TensorFlow 提供统一随机种子与确定性算子配置，但跨硬件、跨 TensorFlow 版本的逐位一致性不能保证；复现实验仍需冻结环境和输入摘要。[TensorFlow 确定性说明](https://www.tensorflow.org/api_docs/python/tf/config/experimental/enable_op_determinism)

安装时先检查 CPU 架构与 Python 版本。TensorFlow 官方安装矩阵目前列出 Apple Silicon 等平台的 wheel，并说明 macOS x86 支持停留于 2.16 系列。应以最终实际安装成功并经过测试的版本写入锁定依赖，不直接把“最新版”作为可复现承诺。[TensorFlow 安装与支持矩阵](https://www.tensorflow.org/install/pip)

## 7. 首期验收建议

1. 从空数据目录启动，生成带地图的世界和至少一段完整历史；相同种子可以重放。
2. 导入统一 CSV/JSON/GeoJSON 真实数据样本，拒绝无效时间、未知区域、重复订单和非法数值，并输出质量报告。
3. 训练真实 TensorFlow/Keras 网络，保存后在新进程重载并完成预测；不得以随机数或手写公式冒充模型。
4. 证明时间边界、滞后特征和归一化无泄漏；以统一测试集比较至少一个基线与神经网络。
5. API 覆盖世界、地图、仿真、数据集、训练、任务状态、模型指标与预测，返回 OpenAPI 契约，能被独立前端接入。
6. 对关键领域约束、导入错误、训练状态和预测兼容性进行测试，并记录真实执行命令与结果。
7. Git 按调研/骨架、仿真与数据、模型管线、API、验证与交接推进；不把大型模型、数据库、原始订单和虚拟环境提交入库。
