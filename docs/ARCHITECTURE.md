# 架构决策与实施阶段

## 目标与边界

以 Python、TensorFlow/Keras 完成可复现的网约车需求预测后端，交付可运行系统、离线评估、API 与前端交接资料。包含虚拟地图和场景模拟，真实数据可经适配器接入。前端由后续项目实现。

## 选择：模块化单体 + 独立 worker

FastAPI + Pydantic 提供版本化 REST/OpenAPI；SQLite WAL 保存资源、模型和持久任务队列；不可变目录保存 GeoJSON、Parquet、原生 `.keras` 模型与指标。API 与 worker 独立进程，训练不阻塞 HTTP。数据域、仿真域、机器学习域与仪表盘聚合域解耦；相同数据格式连接虚拟和真实数据。

比较：全量微服务/PostgreSQL/PostGIS/Redis/Celery 增加课题启动成本，留为多机扩展；API 进程内 BackgroundTasks 缺少重任务隔离和持久恢复，不适合训练；单脚本/Notebook 无法支撑仪表盘、模型版本与联调。SQLite 的目标是单机中小规模，队列使用事务原子认领，单 worker 串行任务降低内存峰值。

## 预测设计

按区域和小时汇总发起请求，零需求桶显式保留。共享 GRU 编码历史需求/邻域需求/滞后乘客与外因，结合区域属性与未来已知日历，直接多步输出非负需求。共享模型兼容不规则真实区域；ConvLSTM 依赖规则栅格，图神经网络训练/运维复杂度更高，保留邻接矩阵升级方向。每次训练与季节性基线公平比较，按时间隔离目标窗口，验证集调参，测试集只报告；不保证神经网络一定优于基线。

## 数据真实性

合成数据只能证明软件与仿真条件下的效果，不能证明真实业务精度。真实已完成行程无法还原取消或未响应需求，导入必须标记 target_semantics。天气默认使用预测起点已知值持续假设，事件/节假日按事先计划；未来实测天气不能作为默认预测输入。

## Git 阶段

1. M0：调研、契约、架构与工程脚手架。
2. M1：虚拟地图、仿真、真实数据导入与质量检查。
3. M2：特征、真实模型训练、时序评估与预测。
4. M3：持久任务、仪表盘 API、完整联调。
5. M4：回归验证、实测报告、交接资料与发布标记。

最终实施细节以代码、OpenAPI 与 HANDOFF 为准。
